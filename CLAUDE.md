# CLAUDE.md — HR Portal (Sri Lanka HRMS SaaS)

Read this file fully at the start of every session. Then read `docs/PLAN.md` and work **only on the phase the user names**.

## What we are building
A sellable, multi-client HR portal for Sri Lankan mid-size companies (50–1,000 employees).
v1 = Core HR + Leave + Attendance + full Sri Lanka payroll + Employee self-service PWA.
Every client gets its **own Supabase project** (database, auth, storage). A small **control plane** knows about all clients.

## Stack (do not change without asking)
- Monorepo: pnpm workspaces + Turborepo
- `apps/api` — Node 20+, TypeScript (strict), Express 5, Zod, Drizzle ORM (postgres.js driver), pino logging
- `apps/web` — Next.js (App Router), TypeScript, Tailwind + shadcn/ui, TanStack Query, React Hook Form + Zod, Serwist for PWA
- `packages/shared` — Zod schemas + inferred types shared by api and web (single source of truth for API contracts)
- `packages/db` — Drizzle schema + SQL migrations for the **tenant** database
- `packages/control-db` — Drizzle schema + migrations for the **control plane** database
- `packages/payroll` — pure, framework-free payroll/statutory calculation engine (no DB, no I/O)
- `packages/config` — shared tsconfig, eslint, prettier
- Tests: Vitest (unit/integration), Playwright (e2e)
- Postgres: Supabase (region ap-southeast-1 Singapore unless told otherwise)
- Jobs: pg-boss on the control-plane database (job payload always carries `tenantId`)
- Email: provider behind an `EmailSender` interface (Resend or SMTP)
- PDFs: PDFKit on the server

## Hard rules
1. **No statutory or business constants in code.** EPF/ETF %, APIT tables, OT multipliers, working-day divisors, leave entitlements, rounding — all live in tenant DB config tables with `effective_from` dates and are seeded with defaults. Code reads config for the relevant date. A test must fail if a rate is hard-coded in `packages/payroll`.
2. **Money:** stored as `numeric(14,2)` in Postgres; calculated with `decimal.js` in TS. Never use JS `number` arithmetic for money. Rounding mode comes from tenant config.
3. **Dates:** business dates are Postgres `date` (no time). Timestamps are `timestamptz`. All "which day is it / is this a weekend" logic uses the tenant timezone (default `Asia/Colombo`) via `date-fns-tz` helpers in `packages/shared/time`. Never call `Date#getDay()`/`setHours()` on server-local time.
4. **Tenant isolation:** every request resolves a tenant (subdomain → control plane) and gets `req.ctx = { tenant, db, user, employee, permissions }`. Handlers use `req.ctx.db` only. There is no global tenant DB client. A missing tenant = 404 before auth.
5. **Browser never talks to Postgres.** The web app uses Supabase only for Auth. All data goes through the Express API. RLS is enabled on every tenant table with **no policies** (deny-all for `anon`/`authenticated`) as defence in depth.
6. **Every endpoint:** Zod-validated input (schemas from `packages/shared`), permission check, and the standard envelope `{ success: true, data } | { success: false, error: { code, message, details? } }`.
7. **Authorization = permission + scope.** Permissions are `module.action` (e.g. `leave.approve`); scope is `self | team | all`. Every list/detail query must apply scope. Write an IDOR test for every new resource (employee A cannot read employee B; manager cannot see outside team).
8. **Audit log:** every create/update/delete on HR data writes `audit_log` (actor, entity, entity_id, before, after, ip, at) through the shared repository helper — not ad hoc.
9. **Multi-step writes use transactions** (leave balance + request, payroll run + lines, etc.).
10. **Ledgers over counters:** leave balances are derived from a `leave_ledger` (accrual, carry-forward, taken, adjustment, expiry entries); never mutate a "used days" counter directly.
11. **Payroll engine is pure:** `calculatePayslip(inputs, config) → result` with a full calculation trace. Golden-file tests in `packages/payroll/__fixtures__` must pass before any payroll PR is done.
12. **Migrations** are forward-only SQL files generated by drizzle-kit, reviewed by hand, and must run on every tenant via `pnpm tenants:migrate`. Never edit an applied migration.
13. Don't add a dependency without saying why in the PR/commit message.
14. `reference/uqms-hr/` (if present) is the old Mongo implementation. Use it to understand behaviour/screens only. **Do not copy code from it.**

## Working style for each phase
1. Enter plan mode, read the phase in `docs/PLAN.md`, list the files you'll touch and any open questions. Wait for approval.
2. Work in small vertical slices: migration → shared schemas → API + tests → UI → e2e.
3. Run `pnpm typecheck && pnpm lint && pnpm test` before declaring a slice done.
4. Update the phase checklist in `docs/PLAN.md` (tick boxes) and add notes under "Decisions log" at the bottom.
5. Stop and ask when a requirement is legally/financially ambiguous (payroll, tax, statutory reports). Do not guess Sri Lankan law.

## Commands (create these in Phase 0)
- `pnpm dev` — api + web
- `pnpm test` / `pnpm test:e2e`
- `pnpm db:generate` — drizzle-kit generate for tenant schema
- `pnpm tenants:migrate [--tenant=<slug>] [--dry-run]`
- `pnpm tenant:create --slug acme --name "Acme (Pvt) Ltd" --admin-email hr@acme.lk`
- `pnpm seed:demo --tenant=<slug>`

## Naming
- DB: snake_case tables, plural (`employees`, `leave_requests`); PK `id uuid default gen_random_uuid()`; `created_at`, `updated_at`, `created_by`, `updated_by` on every table; soft delete via `archived_at` only where stated.
- API: `/api/v1/<resource>`; kebab-case paths; plural nouns.
- Web routes: `/(app)/<module>/...`, self-service under `/(app)/me/...`.
